# Taste
- Prefers repo/process hygiene and curation: when a batch of goal work is done, revisit and archive completed plan/spec/tasks docs into `docs/archives/` per the repo's strict-driven-development retention policy (don't leave finished goal folders cluttering `docs/features`/`docs/issues`). Prefers organizing a large batch of changes into multiple focused, coherent, independently-mergeable PRs by feature boundary (and avoiding file-level overlap between them) rather than one monolithic "one big pr", splitting by goal/feature and verifying each branch independently. Confidence: 0.7
- Prefers the codebase to use base-ui for UI primitives; code still using the old radix-ui implementation/patterns should be migrated to base-ui (e.g., tabs). Confidence: 0.9
- Prefers `style.css` (design tokens/theme) to match the official shadcn ui style.css — simple, canonical semantic vars (`--background`, `--card`, `--sidebar`, etc.) — and regards custom re-declarations of Tailwind defaults, duplicated `--color-*`/`--radius-*` blocks, and legacy theme variables as noise ("too many repeated stuff... missing some of them or giving bad variables"). Confidence: 0.85
- Treats the official shadcn/ui reference files (registry `style.css`, component sources) as the source of truth for correct styling setup; deviations from them are called out as problems. Confidence: 0.75
- Uses shadcn wrapper components (imported from `@/components/ui/*`, e.g. `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent`) rather than importing base-ui primitives directly; the canonical shadcn usage pattern (e.g. `defaultValue` + one `TabsContent` per tab) is the reference for correct usage. When adding a new shadcn/base-ui wrapper component, grep the existing codebase for prior call sites of that wrapper BEFORE writing it — shadcn wrappers over base-ui often have undocumented structural requirements (e.g. `DropdownMenuLabel` requires a `DropdownMenuGroup` parent for `MenuGroupContext`, or the menu crashes at runtime) that aren't visible from the prop types alone; guessing the structure causes a runtime crash the user will only see after a page mount, so the right time to learn the wrapper shape is from existing files, not from a post-hoc error report. Confidence: 0.85
- For shadcn/Base UI `DropdownMenu`, the canonical structure is: the `render` prop on `DropdownMenuTrigger` is a self-closing element (the bare trigger button shell, e.g. `<button className="..." />`) and ONLY the trigger's visible content (icon/label/chevron) is passed as JSX children of `DropdownMenuTrigger`. `DropdownMenuContent` is a SIBLING of `DropdownMenuTrigger` inside `<DropdownMenu>`, not a child. The shadcn `DropdownMenu` (and Base UI's `Menu.Root`) expects `DropdownMenuContent` as a sibling; when it's a child of `DropdownMenuTrigger`, the content gets rendered as a literal DOM child of the trigger button instead of a portal-positioned popup, and clicks never open the menu. The correct shape is: `<DropdownMenu> <DropdownMenuTrigger render={<button ... />}>{visible content}</DropdownMenuTrigger> <DropdownMenuContent>...</DropdownMenuContent> </DropdownMenu>`. The user caught an instance where the assistant put `DropdownMenuContent` inside the trigger's children and the dropdown silently failed to open — when in doubt, copy the structure of an existing working call site (e.g. `WorkspaceSelector`, `ChatTopBar` menus) byte-for-byte instead of guessing. Confidence: 0.9
- Architectural principle: the daemon must be able to run fully headless and own ALL DB/persistence work. The desktop shell must not handle or touch the database — any desktop-owned DB/persistence stack (e.g. sqlitePresenter, sync/project/session persistence) is a blocker and should be deleted or migrated to the daemon, never left to the desktop. The daemon being the single owner of persistence is treated as mandatory, not a nice-to-have. Confidence: 0.85
- Prefers aggressive removal of dead/legacy code without hedging or per-item confirmation — "remove everything dead/legacy, i will tell you if something is broken" — i.e., the user will catch regressions themselves, so the agent should just execute the cleanup decisively. Confidence: 0.8
- On open PRs, expects the agent to proactively triage and work through AI review comments (Copilot, Greptile, React Doctor): genuinely-valid findings (real bugs, misleading/deceptive UX, security gaps, premature doc archiving) get fixed, while advisory/informational items get a reply explaining design intent instead of a blind change; each PR gets a concise summary comment listing what was addressed, and when a finding's root cause lives in a different PR (e.g. a shared logger change), the fix is cross-referenced on both. Confidence: 0.75
- Wants new/experimental features to be user-controllable from the Settings page: a question like "users can enable disable this?" means add a proper Settings toggle (a `Switch` persisted via the daemon's config-entries contract, e.g. `thread_sidebar_enabled`, default off, same pattern as `sidebar_group_mode`) — not just an app-bar affordance; disabling the flag must also hide the feature's UI entry points (app-bar button, panel). Confidence: 0.85
- Config-entry read paths exist in TWO places that must be kept in sync: the desktop main copy of `configRouteSupport.ts` (`apps/desktop/src/main/routes/config/`) and the daemon's backend-core copy (`packages/backend-core/src/dispatch/config/`). The settings window runs over the daemon bridge, so adding a key to only the desktop copy silently drops it (flag reads as default `false`) while the output schema still validates — resulting in confusing Zod "expected object, received undefined" errors. Any new/changed config entry must be added to both dispatch copies. Confidence: 0.75
- Prefers keeping test infrastructure lean for experimental features: when renderer/component test setup proves fragile (vitest/jsdom/React-version resolution friction), drop the new unit-test scaffolding entirely (vitest config, setup file, tests, added devDeps) rather than forcing it through, and rely on existing route tests plus format/lint/typecheck as the quality gates. Confidence: 0.6
- For Settings toggles persisted via config, load the flag exactly once on mount through a stable ref (`useRef`) and keep the setter optimistic: a `useEffect` whose dep is a hook that returns a fresh object identity every render (e.g. `[threadSidebar]`) re-fires after each render and overwrites the just-toggled value with a stale read — the visible symptom is the switch "blinking" back off. Confidence: 0.65
- Config-backed Settings toggles must be fully live end-to-end: persisted across restarts AND applied in other windows immediately without an app restart. A toggle that holds in the settings window but doesn't survive or apply elsewhere is reported as broken ("is not persisted. so its not applied", "now is persisted but it seems not used to sho the sidebar"). The correct robust mechanism is event-driven, not focus-based: add a typed `config.entries.changed` event contract (shared-contracts event + catalog), publish it from `config.updateEntries` in BOTH dispatchers (daemon + desktop), surface it via an `onEntriesChanged` helper on the config client (canonical `on*` helper pattern), and subscribe in the store so the main window re-reads the entry live. A window-focus re-read is NOT reliable here — the desktop publishes `window.state.changed`, not the legacy `WINDOW_FOCUSED` event the UI runtime subscribes to, so a focus-based hook silently never fires. Confidence: 0.8
- User reports regressions in terse, symptom-only shorthand ("still cannot toggle sidebar in settings, it just blink", "now i can, but is not persisted. so its not applied", "i dont see the sidebar, whats i supposed to see?") and expects the agent to root-cause and fix the actual runtime behavior without asking clarifying questions — a completed goal with green format/lint/typecheck gates is not proof the fix works; the user will come back if the live behavior is still broken. Confidence: 0.8
- Expects a Settings/config toggle to produce an obvious, immediate visible change in the UI. When enabling a feature only added a subtle affordance (a small "Threads" pill whose panel still requires a click to open), the user reported "i dont see the sidebar" — the enabled state was not discoverable enough and read as broken. When a toggle's visible result is subtle, the agent should trace the end-to-end wiring to confirm it actually works, tell the user exactly which on-screen element to expect, and prefer an unmistakable visible change (e.g., auto-opening the panel on first enable) over a hidden-behind-a-click entry point. Confidence: 0.5
- Windows platform awareness for UI placement: interactive controls must not sit on the right side of the custom app bar — on Windows (`showCustomWindowButtons` false) the OS draws native minimize/maximize/close caption buttons overlaid on that region, so any button there is covered and unreachable ("the button is not reachable"). App-level toggles belong in the left sidebar rail (the always-reachable 48px icon column, visible in both expanded and collapsed sidebar states), styled consistently with the other rail buttons (Search, theme). Confidence: 0.75
- Settings-toggleable features must REPLACE the existing UI surface they extend, not add new parallel affordances: "it must replace the current left sidebar, that's the point of being toggleable in settings, i don't need another button". When an experiment is enabled from Settings it swaps the content of the existing component (e.g., the sidebar's session column renders the thread list instead), and disabling restores the original — no extra buttons, toggles, or side panels for the feature, and any previously-added entry-point buttons must be removed. Confidence: 0.85
- When the user names a specific reference product for a UI design ("how t3code looks"), the implementation must closely follow that reference's actual visual design (row layout, styling tokens, shelf/grouping pattern); an approximation with ad-hoc styling is called out as "you didn't follow how t3code looks". Before building, verify the reference's actual look rather than inventing a similar-but-different design. Confidence: 0.75
- When debugging a third-party library API mismatch (wrong callback signature, wrong return type, etc.), verify the actual API by reading the installed `.d.ts`/source in `node_modules` rather than relying on memory or assuming a similar-looking library's API — e.g. TanStack Store's `subscribe` is `((value: T) => void)` single-arg, not `(state, prev) => void`, and calling the wrong form silently makes the extra arg `undefined`, which then crashes on the first synchronous `setState` propagation. Confidence: 0.8
- For cross-store state derivation (e.g. one store subscribing to another to track a diff/transition), prefer capturing the previous snapshot in a closure variable over assuming a multi-arg `(state, prev)` subscribe callback — most state stores only pass the new state, and a thrown listener body inside a synchronous `setState` propagates out of the original call (visible as the host `setState` appearing to fail). A `let previousX = store.state.x; store.subscribe(s => { diff(s.x, previousX); previousX = s.x; })` pattern is the safe default. Confidence: 0.75
- When a runtime crash's stack trace points into a bundled/minified file rather than source, map the error back to the source line via file:line:column and the surrounding function names in the trace (e.g. column 50 on `subscribe` callback = the `prev` token) before guessing at the cause; column numbers from the bundle often identify the exact wrong expression. Confidence: 0.7
- Enforce a single source of truth + shared resolution priority for the same conceptual value read from multiple components (e.g. "current agent", "active session"). When two components display what should be the same identity but read from different store fields (e.g. one reads `agentStore.selectedAgentId`, another reads the active session's `agentId` and falls back to the first enabled agent), the UI desyncs and the user sees contradictory state (sidebar says "codex" while the welcome headline says "Orchestrator"). The fix is to define one explicit resolution function with a documented priority (e.g. `selectedAgentId` → active session's `agentId` → first Argos agent) and have every component that displays that identity call the same function. The sidebar switcher and the welcome page, in particular, must share the exact same priority so changing one updates the other. Confidence: 0.85
- For state stores, mutate via the public setter/action API (e.g. `setSelectedAgent(targetId)`) rather than reaching into the store with `agentStore.setState((s) => ({ ...s, selectedAgentId: targetId }))` directly. The public API is where validation, side-effects, and bookkeeping (e.g. clearing the selection if the target is disabled) live; bypassing it silently skips that logic and creates a desync where one component sees the new value while the rest of the system still believes the old one. Treat the public setter as the only correct write path unless there's a specific reason to bypass it. Confidence: 0.8
- When debugging a crash from a runtime error log, the user pastes the full console output (ErrorBoundary + react-stack traces, sometimes mixed with unrelated errors like provider 401s) and expects the agent to (a) identify which trace is the actual code crash vs. user-config noise (e.g. a "401 Unauthorized" from a third-party API key check is not a code defect — it's the user's API key being wrong, surfaced via `ProviderApiConfig.tsx:159`), (b) read the `file:line:column` from the stack trace and go directly to that line, and (c) verify the actual type/return shape of the involved store/API against the source file before guessing. Conflating the two classes of error and "fixing" the wrong one wastes a turn. Confidence: 0.85
- Before destructuring or accessing nested fields on the return value of a store helper / selector (e.g. `findChatSelectableModel(...)`, `getChatSelectableModelGroups()`), open the source file and read the actual `interface` and the function body. Do NOT infer the shape from how the function is named, from a similar-sounding helper in another module, or from how the value "should" look. A common failure mode is assuming `getChatSelectableModelGroups().models[i]` is `{ provider: { id }, model: { id, name } }` when the real type is a flat `RENDERER_MODEL_META[]` and groups have `providerId`/`providerName` (no nested `provider`/`model` keys) — typecheck passes because TS infers the wrong structural shape, but the runtime crashes with `Cannot read properties of undefined (reading 'id')` the first time the menu renders. The fix shape (`group.providerId` + `entry.id`/`entry.name` + `group.providerName`) is only discoverable by reading the type, not by pattern-matching. Confidence: 0.8
- Don't invent a new UI primitive when an existing one has a bug or a problem in one place — fix the existing one or use the same canonical primitive correctly in a different surface. The sidebar agent switcher wasn't working (clicks weren't reaching the handler, suspected shadcn `DropdownMenu` quirk); the user explicitly rejected the "build a custom popover" plan and said "I should fix the existing shadcn dropdown rather than reinventing one" and "keep using the shadcn `DropdownMenu`". The right move was: keep the shadcn `DropdownMenu` (it works for share/export/options in the chat top bar, so the component isn't broken — the sidebar surface was the problem), and move the switcher to a surface where the same shadcn pattern already works. Reinforces the existing "use canonical shadcn usage patterns from prior call sites" preference, but adds: when a primitive misbehaves in one place, suspect the surface, not the primitive. Confidence: 0.85
- Place UI affordances in their semantic context, not in a generic container like the sidebar. The switcher belongs in the chat, next to where the agent is actually surfaced" (i.e. the chat top bar and the welcome page's agent badge, where the agent identity is already shown). When in doubt about where a feature belongs, identify the surface that already displays the value — that's where the control should sit. Confidence: 0.85

If a feature is in the wrong place or uses a surface that doesn't work, the faster path is to move it to a surface that already works and ship that. The user explicitly said: "you spent a lot of rounds debugging; the agent switcher is just in the wrong place. fix it / move it" — implying the diagnosis-then-fix path had been too long. The welcome composer page should pass `isSending={isSubmitting}`. The submit click navigates to the chat page on success, so a static "Sent" flash would be invisible — use the in-flight icon/label as the only "I got your click" feedback. Confidence: 0.7

The chevron rotating on dropdown open is the canonical affordance — not decoration. Confidence: 0.7

Specific tell-tales the user flags: (1) duplicate "I am working" signals (spinner + Working-pill + Idle-pill all visible at once) — keep ONE; (2) unearned single-element drop shadows like `shadow-[0_24px_64px_-32px_rgba(0,0,0,0.45)]` — drop, the window already has an elevation system; (3) `text-[11px] font-medium uppercase tracking-wide` mini-headers — switch to `text-xs font-medium` (sentence case, normal weight, no tracking); (4) `bg-card/40` on every chip — pick one backdrop; (5) `motion-safe:animate-spin` on an always-on loader — drop, the working pill carries the cue; (6) `text-muted-foreground/40, /50, /60, /70, /80` opacity stacks — pick 2-3 levels not 5; (7) empty states with icon + 2 ghosted lines of text on a surface whose primary input is right there — drop the empty state; (8) count badges on section headers — drop, the rows are countable; (9) labels that pretend to be a real product name (e.g. "Xhigh · Build" for a stub preset) — use honest placeholders.
