# Plan

## Current State

Verified against the codebase. All of this is being **removed or replaced** by the target model.

- `GET /health` is public and checked before any auth gate; it returns only `status`, `version`, `uptime` (`apps/daemon/src/index.ts:79`).
- `POST /api/v1/route` auth is conditional: `if (!isLocalRequest(request) && token)` (`apps/daemon/src/index.ts:89`). The guard uses bearer auth (`apps/daemon/src/transport/auth.ts:38`). Consequence: a daemon bound to a non-loopback host **with no token configured has no auth at all**.
- `WS /api/v1/events` accepts `?token=` and compares it to the same single shared secret as the bearer token (`apps/daemon/src/index.ts:103`). No sub-protocol, first-message, or cookie auth exists.
- Loopback bypass keys off hostname only: `127.0.0.1 | localhost | ::1` (`apps/daemon/src/index.ts:25`).
- Default bind is `127.0.0.1`, port `9527` (or `0` for auto-assign) (`apps/daemon/src/index.ts:71`, `lifecycle.ts:43`).
- Token sources: `--token`, `ARGOS_TOKEN`, `--with-token` (auto-generate + print) (`lifecycle.ts:27-51`). Token is a 32-char alphanumeric from `Math.random`, **not** a CSPRNG (`lifecycle.ts:95`). All three sources are removed by this model.
- An IP rate-limiter exists: 10 failures / 60s window triggers a 300s lockout (`transport/auth.ts:1-32`); client IP honors `x-forwarded-for` (`transport/auth.ts:6`). The limiter is kept and generalized.
- Desktop sidecar is launched with `host: "127.0.0.1"`, `port: 0`, and **no token** (`apps/desktop/src/main/presenter/sidecarManager/index.ts:49-76`, `lifecyclePresenter/hooks/init/daemonSidecarHook.ts:22-36`). Local safety comes entirely from the loopback bind today; the target replaces this implicit trust with `desktop-bootstrap`.
- No secret crosses the main→renderer boundary for the local daemon: the port IPC handler returns only `{ port, host }` (`apps/desktop/src/main/routes/daemonPortHandler.ts:6`). The target preserves this.
- Remote workspace config stores `remoteUrl` + `authToken` in `WorkspaceEntry` (`packages/shared/src/workspaceConfig.ts:8`), migrated one-way from legacy `ServerConfig` (`workspaceConfig.ts:57`). The renderer's WS adapter uses the token only as `?token=` (`apps/desktop/src/preload/hybridBridge.ts:206`). The `authToken` field and this UI are removed by this model.
- No `AuthContext`, no principal/session concept, and no auth field on `ConnectionState` (`packages/shared-contracts/src/connection.ts:3`) exist anywhere today.

## Target Model

- **Exposure policy** decides which credential classes are accepted.
- **Bootstrap credentials** only create or resume sessions.
- **Session credentials** authorize normal daemon use.
- **Desktop-only capabilities** stay outside daemon auth and are handled by Electron IPC/local API.
- The shared-secret token model is removed entirely; there is no compatibility credential.

## Auth Classes

- `public`: unauthenticated, non-sensitive endpoints. Initial default: `/health` only.
- `bootstrap`: one-time or launcher-provided credentials used only to create a session.
- `authenticated`: all route dispatch, WebSocket events, future WebSocket RPC, and static web UI beyond initial shell.
- `desktop-only`: native OS/window/device operations that are never exposed through daemon network APIs unless explicitly redesigned.

## Surface Inventory

| Surface | Auth Class | `local-only` | `loopback-browser` | `network-accessible` | `relay` |
|---|---|---|---|---|---|
| `GET /health` | `public` | open (minimal) | open (minimal) | open (minimal) | open (minimal) |
| `POST /api/v1/route` | `authenticated` | desktop client (`desktop-bootstrap`) | `browser-session` | `browser-session` or `bearer-session` | `bearer-session` only |

## Credential Types

- `desktop-bootstrap`
  - Generated by Electron main per sidecar launch with a CSPRNG.
  - Not persisted.
  - Not placed in the daemon process argv and not directly displayed to users.
  - Used by desktop-managed local renderer to obtain a session if browser-like access is needed.

- `one-time-token`
  - Short-lived pairing credential.
  - Safe to place in a pairing URL or QR code.
  - Single use.
  - Creates browser or bearer session credentials.

- `browser-session`
  - Preferred browser credential.
  - Stored as HTTP-only same-site cookie when the UI is served by the daemon.
  - Used for HTTP route calls, WebSocket upgrades, and static web access checks.

- `bearer-session`
  - Durable token for non-browser clients, future mobile, CLI, or cases where cookies are not viable.
  - Stored in platform secure storage where available.

## Exposure Modes

- `local-only`
  - Bind `127.0.0.1`.
  - Desktop sidecar default.
  - `/health` public; all other surfaces require `desktop-bootstrap`.

- `loopback-browser`
  - Bind `127.0.0.1`.
  - Intended for daemon-served browser UI on the same machine.
  - Requires browser session or pairing for privileged surfaces.

- `network-accessible`
  - Bind selected LAN address or `0.0.0.0`.
  - Requires explicit user opt-in.
  - Requires authenticated session for all privileged surfaces.
  - No local-bypass behavior for non-loopback clients.

- `relay`
  - Future mode.
  - Relay/cloud provides discovery and reachability only.
  - Daemon still requires `bearer-session` auth.

## AuthContext Shape

Attached to every gated request/connection during implementation. Route handlers stay independent of auth unless they explicitly read this context.

```ts
type CredentialKind =
  | "none"
  | "desktop-bootstrap"
  | "one-time-token"
  | "browser-session"
  | "bearer-session";

type ExposureMode = "local-only" | "loopback-browser" | "network-accessible" | "relay";

interface AuthContext {
  credentialKind: CredentialKind;
  sessionId?: string;       // present for session credentials, absent for bootstrap
  exposureMode: ExposureMode;
  isLoopback: boolean;
}
```

## Exposure Mode Config Shape

```ts
interface DaemonExposureConfig {
  mode: ExposureMode;
  bindHost: string;          // derived and validated from mode
}
```

Resolution rules the implementation must enforce:

- `local-only` and `loopback-browser` bind `127.0.0.1` only.
- `network-accessible` requires explicit opt-in and rejects loopback-bypass for non-loopback clients.
- `relay` requires session auth only.
- Mode is derived from bind host + opt-in flags when a daemon starts; mismatches (e.g. non-loopback host without opt-in) must fail closed, not silently downgrade.

## Enforcement Points

- Add one daemon auth gate before:
  - HTTP route dispatch
  - WebSocket upgrade
  - future WebSocket route RPC handling
  - static web UI serving when protected assets require a session
- Attach an `AuthContext` to requests (fields above).
- Keep route handlers independent from auth unless a route explicitly needs auth context later.

## Storage Policy

- Daemon:
  - stores session records and pairing token metadata in daemon data dir or database.
  - stores server secret material in OS secure storage when available, with restricted-file fallback.
- Electron main:
  - owns ephemeral desktop bootstrap secrets.
  - may hold active local daemon session credentials in memory.
- Electron renderer:
  - must not persist any daemon secret.
  - never receives `desktop-bootstrap`; it is exchanged for a session by Electron main when needed.
- Browser:
  - prefers HTTP-only session cookie.
  - does not need direct token access for normal daemon-served UI.
- Future mobile/native:
  - uses bearer-session token in secure platform storage.

## Removal Sequence

There is no compatibility phase. The shared-secret model is removed in one cutover, ordered to keep the desktop-managed local case working throughout:

1. Introduce `AuthContext` + the single auth gate; Electron main issues `desktop-bootstrap` and the desktop-managed client authenticates with it. Local desktop keeps working.
2. Delete the shared-secret surface: `--token` / `--with-token` / `ARGOS_TOKEN` (`lifecycle.ts`), the bearer checker and `WS ?token=` (`transport/auth.ts`, `index.ts:89-110`), `WorkspaceEntry.authToken` and the remote-workspace token UI (`workspaceConfig.ts`, `RemoteWorkspaceSetup.tsx`, `hybridBridge.ts:206`). After this, remote/mobile access is intentionally unavailable.
3. Add pairing → session (`browser-session` cookie + `bearer-session`) under a follow-up SDD; remote/mobile access returns.
4. Add exposure-mode selection UI with explicit `network-accessible` opt-in.

Steps 1 and 2 may land in the same implementation SDD/PR; the ordering only constrains that the desktop-managed client is authenticated before the old surface is deleted.

## Test Strategy

This is a model SDD; it ships no implementation. Validation is split between document-level checks now and tests owned by follow-up SDDs.

Document-level (this SDD):

- Every surface in the inventory maps to exactly one auth class.
- Every credential type has a documented issuer, lifetime, storage location, and revocation path.
- Every exposure mode has a bind-host rule and a fail-closed mismatch rule.
- No `legacy-token` / shared-secret credential exists anywhere in the model.
- No `[NEEDS CLARIFICATION]` remains in this folder before any follow-up implementation SDD starts.

Property assertions follow-up implementation SDDs must cover:

- `/health` never returns user identifiers, project paths, provider names, or model config in any exposure mode.
- Non-loopback request with no credential is rejected on every privileged surface in every mode.
- `desktop-bootstrap` secret never appears in daemon argv, on disk, or in renderer-accessible state.
- No shared-secret token surface remains: requests bearing `Authorization: Bearer` for a raw daemon token, or `?token=` on WebSocket upgrade, are rejected after removal.
- Rate-limiting covers bootstrap, session, and pairing verification paths.
- Exposure-mode mismatch (non-loopback host without opt-in) fails closed.

Concrete test ownership:

- Sidecar bootstrap secret lifecycle + transport: sidecar/session-auth implementation SDD.
- WebSocket auth envelope (bearer header vs first-message): `daemon-transport-runtime`.
- Cookie origin binding + pairing flow: pairing/headless-web SDD.
- Exposure-mode fail-closed and bind-host validation: daemon exposure-settings SDD.

## Security Notes

- The target model uses no query-string secrets; WebSocket auth is cookie (browser) or bearer header / first-message (non-browser) to avoid log/history leakage.
- `/health` must never include user identifiers, project paths, provider names, or model configuration.
- Network exposure must require explicit confirmation and authenticated privileged access.
- Relay/cloud identity must not replace daemon session auth.
- `x-forwarded-for` trust is an implementation concern; the model assumes the daemon only honors it behind an explicitly trusted proxy configuration, not by default.
